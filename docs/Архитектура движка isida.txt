Архитектура симбиотической системы ISIDA: формальное описание

Версия 3.6 (рецензия v3.5: спецификация движка §12, дорожная карта триады §13)

Статус документа: архитектурный канон + инженерная спецификация реализованных механизмов (§1.6–1.7, §5.0–5.2) +
MVP-диады (§5.3, §6.7–6.14). Спецификация движка для валидации — §12.
Дорожная карта приведения к триаде — §13. Границы применимости — §11.

Методологическая оговорка: документ описывает архитектуру ISIDA, инспирированную нейробиологией, но не претендует
на строгое биологическое соответствие. Там, где принято инженерное упрощение (временное окно УР, отключение ISIDA-OR
на 4+, жёсткое разделение Operator/Niche), это явно помечено как «архитектурное решение ISIDA», а не «биологический факт».
Полное ТЗ — следующий уровень; параметры threshold/K/веса фазы B — калибруются экспериментально.

0. ЗАЧЕМ ТРИАДА: ФОРМАЛЬНОЕ ОБОСНОВАНИЕ
═══════════════════════════════════════════════════════════════════════════════

0.1. Дефект схемы «оператор + симбионт»

В конфигурации «оператор → симбионт» один внешний агент совмещает три роли:

  1. Источник стимулов (среда).
  2. Источник оценки действий (учитель).
  3. Единственный канал, через который симбионт связан с «реальностью».

При отсутствии сигналов с пульта симбионт остаётся без структурированной среды; 
ритмический дрейф параметров — прототип метаболизма, но не экология. При наличии только пульта симбионт учится не адаптации к миру, 
а угождению единственному источнику стимулов и оценок — то есть перестаёт быть автономной системой в смысле базового принципа ISIDA: 
«симбионт не выполняет внешние команды, а поддерживает гомеостаз через взаимодействие со средой».

0.2. Минимально необходимая конфигурация

Разделение на три участника:

  ┌─────────────┬──────────────────────────────┬────────────────────────────────────────────┐
  │ Участник    │ Функция                      │ Что предоставляет                          │
  ├─────────────┼──────────────────────────────┼────────────────────────────────────────────┤
  │ Оператор    │ Педагог, экспериментатор     │ Форму поведения (ритуал, демонстрация,     │
  │             │                              │ провокация); начальную настройку на        │
  │             │                              │ ранних стадиях                             │
  ├─────────────┼──────────────────────────────┼────────────────────────────────────────────┤
  │ Среда       │ Реактивный связанный партнёр │ Причинно-следственную обратную связь на    │
  │ (Niche)     │                              │ действия существа; автономную динамику     │
  ├─────────────┼──────────────────────────────┼────────────────────────────────────────────┤
  │ Существо    │ Объект исследования          │ Интеграцию формы и обратной связи в        │
  │ (Creature)  │                              │ собственную организацию                    │
  └─────────────┴──────────────────────────────┴────────────────────────────────────────────┘

Ключевой постулат: триада «существо–среда–оператор» — не опциональное усложнение, а минимальная единица анализа развития автономного поведения в ISIDA.

0.3. Принцип разделения оценки и педагогики

  • Оценка (полезность действия, знак результата) извлекается существом из динамики
    собственного гомеостаза после отклика среды. Это внутренний сигнал, не сообщение
    «от среды» в педагогическом смысле.

  • Среда не «учит» — не посылает целевых воздействий с педагогической интенцией,
    не участвует в контуре «оператор ↔ ученик». Она реактивна: меняет своё состояние
    в ответ на действия существа и от собственной гомеостатической динамики;
    изменение coupling отражается на гомеостазе существа.

  • Оператор не является финальным судьёй на зрелых стадиях. Он задаёт форму
    (ритуальное подстраивание) и может косвенно воздействовать на существо через
    среду. Прямое изменение параметров существа — только bootstrap и аварийный режим.

0.4. Влияние Niche на гомеостаз и «оценка»: разведение понятий

Фраза «Niche не посылает +1/−1 и не воспитывает» не означает, что среда не влияет
на гомеостаз Creature. Niche обязана влиять на параметры гомеостаза Creature как
физическая реальность его цифрового мира — через coupling, реактивную обратную связь,
автономную динамику.

Разводятся два уровня:

  ┌──────────────────────┬─────────────────────────────────────────┬──────────────────────────────┐
  │ Уровень              │ Смысл                                   │ Кто / что                    │
  ├──────────────────────┼─────────────────────────────────────────┼──────────────────────────────┤
  │ Каузальное влияние   │ Изменение параметров гомеостаза Creature│ Niche → coupling →           │
  │                      │ вследствие отклика Niche на действие    │ `InfluenceActionSystem` /    │
  │                      │                                         │ мост хоста                   │
  ├──────────────────────┼─────────────────────────────────────────┼──────────────────────────────┤
  │ Извлечение оценки    │ Знак полезности действия, прочитанный   │ Creature → AOE               │
  │                      │ Creature из Δгомеостаза                 │ (`ComputeOperatorAutomatizm  │
  │                      │                                         │ Assessment`, integral state) │
  └──────────────────────┴─────────────────────────────────────────┴──────────────────────────────┘

Niche — источник оценки по факту, Creature — тот, кто читает приговор из собственного
тела. Среда не шлёт явный педагогический сигнал («правильно/неправильно»); знак
результата извлекается симбионтом из знака гомеостатического отклика. В коде влияние
и оценка разведены по разным методам; в каноне первичный триггер AOE — отклик Niche,
не ответ оператора.

«Не воспитывает» = Niche не имеет педагогического намерения: не подстраивает отклик
под учебный план оператора, не зеркалит учителя, не участвует в контуре
«оператор ↔ ученик». Воспитание — функция Operator (форма, ритуал); выживание
в среде — функция Creature ↔ Niche.

0.5. Цель адаптации и угасания Operator

Задача Creature — адаптироваться в Niche, а не угождать Operator.

  ┌─────────┬────────────────────────────────────────────────────────────────────────┐
  │ Стадии  │ Роль Operator                                                          │
  ├─────────┼────────────────────────────────────────────────────────────────────────┤
  │ 0       │ Первичные настройки: начальные аттракторы, bootstrap-переопределение   │
  ├─────────┼────────────────────────────────────────────────────────────────────────┤
  │ 1–3     │ Постепенное ослабление прямого воздействия на гомеостаз Creature;      │
  │         │ ритуализация, подстраивание                                            │
  ├─────────┼────────────────────────────────────────────────────────────────────────┤
  │ 4+      │ Рутинное вмешательство только через Niche; прямое переопределение      │
  │         │ Creature — аварийный режим                                             │
  └─────────┴────────────────────────────────────────────────────────────────────────┘

Operator финализирует не «обучение навсегда», а свёртку педагогической поддержки
(рутинной): симбионт продолжает жить в диаде с Niche; Operator остаётся для
аварийного режима, калибровки, мета-сигналов.

Схема «Operator заменяет Niche» не выращивает автономию: Operator эфемерен, его
реакции зависят от намерения, а не от coupling. Такой симбионт не готов к жизни
в «реальной» среде — будь то приложение офиса, программный контур или физический
мир робота.

Контуры: Niche — партнёр-симбионт; контуры — адаптеры к внешнему миру (API
офисного приложения, симулятор, датчики робота). Цифровой симулятор — один из
возможных поставщиков контуров на этапе разработки; физический мир — другие
контуры при том же контракте coupling.

0.6. Виртуальная vs реальная среда: разбор возражения

Возражение: симбионт должен воспитываться только в «реальной» среде; иначе —
исполнитель по команде; виртуальная среда статична, т.к. это программа.

Где возражение верно: если «среда» = статичный скрипт или Operator вместо среды,
симбионт учится угождать источнику стимулов — это исполнитель по команде. Нужна
нестационарная связанная динамика, а не независимая награда от учителя на каждом
шаге (независимые одинаково распределённые воздействия).

Где возражение неверно (категоричность «только реальная»):

  • «Виртуальная = статичная» — ложная дихотомия. Программа может быть адаптивной
    Niche-симбионт, живой системой (офис, ОС, сеть, мультиагентная), стохастическим
    или коадаптивным процессом. Статична не «цифра», а архитектура без связанной
    автономии.

  • «Реальная» физическая среда тоже может быть тривиальной (лабораторный полигон).
    Робототехника: перенос симуляция→реальность — перенос контуров, не магия
    материальности.

  • Исполнитель по команде vs симбионт определяется архитектурой обратной связи:
    Operator = среда + судья → исполнитель по команде; Niche = первичный каузальный
    контур, Operator угасает → симбионт.

Критерий пригодности среды: не «биты vs атомы», а перенос — сохраняются ли
automatisms/rules при смене экземпляра Niche без переобучения Operator (§6.6).

Оговорка MVP vs полная автономия (рецензия §0.6): на фазе A допустима слабо
динамичная или статичная Niche — baseline ≈ 0, навык различения «действие vs фон»
ещё не требуется. Полное различение спонтанной динамики Niche и обусловленного
отклика — обязательное условие фазы B+ (§5.3.1); до его реализации система остаётся
в режиме педагогической песочницы, а не эксплуатационной автономии. Это не
противоречие «виртуальная ≠ статичная», а поэтапное наращивание сложности среды.

0.7. Педагогическая песочница: щадящие условия обучения

Обучение всегда начинается в щадящих, частично искусственных условиях — иначе
нельзя. Аналогия: студент в университете «живёт» в педагогической песочнице —
учебный план, сценарии, дедлайны, лабораторные работы. Это тоже «виртуальная»
среда в широком смысле: ситуации модулируются, опасность снижена, отрабатываются
ритуалы и паттерны (не «что делать в катастрофе», а «что делать, чтобы катастрофа
не возникла»).

Отрицать упрощение и виртуализацию на этапе обучения — противоречить практике
передачи навыков (подстраивание, Выготский, Соколянский–Мещеряков). Никто не
обучает в «боевых» условиях, если есть выбор: потери неприемлемы, обучение
бессмысленно по результату.

Следствие для ISIDA:

  ┌──────────────────┬────────────────────────────────────────────┬─────────────────────────────┐
  │ Фаза             │ Характер «среды»                           │ Аналог                      │
  ├──────────────────┼────────────────────────────────────────────┼─────────────────────────────┤
  │ A–B              │ Педагогическая песочница: Operator         │ Университет, тренажёр       │
  │                  │ модулирует Niche, сценарии, ритуалы        │                             │
  ├──────────────────┼────────────────────────────────────────────┼─────────────────────────────┤
  │ C                │ Niche с большей автономией; Operator       │ Стажировка, полевые         │
  │                  │ только через Niche                         │ условия с надзором          │
  ├──────────────────┼────────────────────────────────────────────┼─────────────────────────────┤
  │ После угасания   │ Niche с эксплуатационными контурами        │ Профессиональная среда      │
  │                  │ (офис, робот, живой API)                   │                             │
  └──────────────────┴────────────────────────────────────────────┴─────────────────────────────┘

Педагогическая песочница не противоречит триаде: Operator и Niche на ранних фазах
создают щадящую экологию; цель — перенос в более сложные контуры, а не вечная жизнь
в лаборатории. Требование «только реальная среда с первого такта» смешивает целевой
контур (эксплуатация) с методом обучения (песочница) и блокирует угасание.

0.7.1. Песочница vs эксплуатация: континуум, не бинарность

«Песочница» и «эксплуатация» — не два режима с жёсткой границей, а континуум
параметров диады. Operator всегда может воздействовать через Niche; различие —
в интенсивности, предсказуемости и автономии Niche.

  ┌────────────────────────────────────┬─────────────────────┬──────────────┬─────────────────────────┐
  │ Параметр                           │ Песочница (A–B)     │ Переход (C)  │ Эксплуатация            │
  ├────────────────────────────────────┼─────────────────────┼──────────────┼─────────────────────────┤
  │ Частота вмешательств               │ Высокая, по         │ Снижается    │ Редкая (калибровка,     │
  │ Operator → Niche                   │ сценарию            │              │ сбои)                   │
  ├────────────────────────────────────┼─────────────────────┼──────────────┼─────────────────────────┤
  │ Предсказуемость динамики Niche     │ Повышенная          │ Средняя      │ Близка к автономной     │
  │                                    │ (модулируется)      │              │                         │
  ├────────────────────────────────────┼─────────────────────┼──────────────┼─────────────────────────┤
  │ Прямое переопределение Creature    │ Допустим /          │ Заблокирован │ Только аварийный режим  │
  │                                    │ ограничен           │              │                         │
  ├────────────────────────────────────┼─────────────────────┼──────────────┼─────────────────────────┤
  │ Coupling                           │ Упрощённый допустим │ Полный       │ Полный                  │
  ├────────────────────────────────────┼─────────────────────┼──────────────┼─────────────────────────┤
  │ Критерий перехода                  │ —                   │ Тест переноса│ Эксплуатация в целевых  │
  │                                    │                     │ (§6.6) +     │ контурах                │
  │                                    │                     │ угасание     │                         │
  └────────────────────────────────────┴─────────────────────┴──────────────┴─────────────────────────┘

Операционный критерий выхода из песочницы: automatisms/rules, выученные на Niche₁,
сохраняются на Niche₂ (та же структура coupling, другие параметры) без переобучения
Operator. До прохождения переноса — режим остаётся с доминированием песочницы,
даже на стадии 4+.

1.1. Симбионт

Автономная система, поддерживающая внутренний гомеостаз через непрерывное
взаимодействие со средой. Не выполняет внешние команды. Все проявления подчинены
удержанию параметров существования в целевых пределах.

Таксономия по функциональной роли (в рамках экспериментального среза):

  • Симбионт-существо (Creature) — объект исследования; полный стек механизмов
    (стадии 0–5).

  • Симбионт-среда (Niche) — реактивный связанный партнёр. Не педагог, не судья.
    Имеет редуцированный активный стек в данной роли (§1.4).

  • Оператор (Operator) — внешний деятель вне операционного замыкания симбионта.
    Источник формы поведения и инженерных возмущений с фазозависимыми полномочиями.

1.2. Функциональная относительность ролей

Роль симбионта (Creature или Niche) определяется положением в рассматриваемом
срезе вложенной структуры, а не статическим «рангом» системы.

  • Один и тот же симбионт может быть Niche для Creature нижнего уровня и Creature
    в Niche верхнего уровня.

  • Стек симбионта един (один `IsidaEngine`, одни подсистемы); различие
    Creature/Niche — RoleProfile (маска активных подсистем) в рамках наблюдательного
    среза (срез эксперимента: кто для кого среда в данном прогоне).

Следствие: при смене фокуса исследования Niche может быть развёрнута до Creature
(активируются верхние уровни стека). Механизм — динамический RoleProfile, а не
статическая «урезанная версия навсегда».

1.3. Среда: разведение понятий

  ┌─────────────────────────┬────────────────────────────────────────────────────────┐
  │ Термин                  │ Смысл                                                  │
  ├─────────────────────────┼────────────────────────────────────────────────────────┤
  │ Симбионт-среда (Niche)  │ Физическая/экологическая среда существа; реактивный    │
  │                         │ партнёр с гомеостазом, рефлексами, coupling            │
  ├─────────────────────────┼────────────────────────────────────────────────────────┤
  │ Информационная среда    │ Внутренний интегративный кадр существа («что ситуация  │
  │ (IE)                    │ значит для меня»). Не Niche                            │
  └─────────────────────────┴────────────────────────────────────────────────────────┘

1.4. Минимальный стек в роли Niche

  • `GomeostasSystem` — обязательно.
  • Безусловные рефлексы — обязательно.
  • Условные рефлексы (стадия 1) — опционально, ограниченно.
  • Автоматизмы (стадия 2) — только реактивные; без контура ожидания оценки
    оператора, без зеркалирования оператора.
  • Психика (2+), зеркальные автоматизмы (3), эпизодика (4+), циклы мышления —
    не активированы в роли Niche.

Niche не нейтральный фон: она имеет собственную динамику (дрейф, рефлексы,
автономные изменения). Она реактивна в отношении Creature: отклик на его действия
+ спонтанная динамика, которую Creature должен отличать от отклика (§4.5, §4.6).

1.5. Рекурсивная вложенность

Niche может быть Creature в среде более высокого порядка. Практическая глубина
экспериментов: 1–2 адаптивных уровня; выше — неадаптивные граничные условия.


1.6. Система гомеостаза (`GomeostasSystem`): реализация

Центральный модуль: `GomeostasSystem` + `HomeostasisCalculator`. Гомеостаз в ISIDA —
не метафора, а вычислимая подсистема с явными структурами данных и тактовым циклом.

1.6.1. Параметры (`ParameterData`)

  ┌──────────────────┬────────────────────────────────────────────────────────────┐
  │ Поле             │ Семантика                                                  │
  ├──────────────────┼────────────────────────────────────────────────────────────┤
  │ Value            │ Текущее значение (0…100)                                   │
  │ NormaWell        │ Целевое «хорошее» значение                                 │
  │ Speed            │ Направление дрейфа: Speed<0 — дефицит (плохо ниже нормы),  │
  │                  │ Speed>0 — избыток (плохо выше нормы)                       │
  │ Weight           │ Вес в интегральном состоянии (0…100)                       │
  │ IsVital          │ Жизненно важный параметр (участвует в оценке AOE, Danger)  │
  │ CriticalMin/Max  │ Границы критического состояния (смерть симбионта)          │
  └──────────────────┴────────────────────────────────────────────────────────────┘

Иерархия целей (ответ на рецензию «неопределённость гомеостаза»):

  1. Критические (IsVital): выход за CriticalMin/Max → смерть; ухудшение в зоне Bad
     → Danger, VeryActualSituation; приоритет в `ComputeOperatorAutomatizmAssessment`.
  2. Некритические: влияют на интегральное состояние и стили, но не на немедленную
     угрозу существования.
  3. Разрешение конфликта: при одновременных Bad и Well отклонениях
     `CalculateAgentState` сравнивает относительные взвешенные суммы (relativeThreshold
     ≈ 30%) и выбирает более выраженное состояние; при равенстве — Bad имеет приоритет
     над Well в паре «оба значимы».

1.6.2. Тактовый цикл (`UpdateStateOnly`, каждый пульс `GlobalTimer`)

  1. Сравнение с снимком предыдущего пульса → `HasCriticalParameterChanges` (игнорирует
     шаг дрейфа |Speed|/100 как шум).
  2. Для каждого параметра: `UpdateState(dynamicTime, difSensorPar)` — состояние
     Bad/Normal/Well с временным удержанием (`LastStateChangePulse`).
  3. Пульсовый дрейф: `Value += Speed/100` (в сне /10), если включён
     `HomeostasisPulseSpeedDriftEnabled`.
  4. `CalculateAgentState` → интегральное состояние Bad/Normal/Well (`CurrentOverallState`).
  5. Обновление IE: Danger, mood (`HomeostasisMoodPerception`), VeryActualSituation,
     активные стили реагирования (`BehaviorStyle` через `StyleActivations`).
  6. `UpdateNoveltyDetector` → `AppGlobalState.IsNewConditions`.
  7. Сохранение снимка параметров для следующего пульса.

Порядок важен: внешнее влияние (`InfluenceActionSystem`, coupling Niche) записывает Value
до дрейфа; иначе дельта «удара» от среды схлопывается до шага Speed.

1.6.3. Внешнее влияние

`InfluenceActionSystem` / `HostBatchUpdateParameterValues` изменяют Value параметров;
затем `OnExternalInfluenceApplied()` пересчитывает интегральное состояние без ожидания
следующего пульса. Это канал Operator/Niche → гомеостаз Creature.

1.6.4. Стили и доминирование

`BehaviorStyle` активируются по зонам параметров (0–6). Антагонизм стилей задаётся
`StyleAntagonism`. Доминирующий параметр (`FindDominantParameter`) определяет фокус
при оценке автоматизма и выбор реакции. `StyleCombinationsManager` управляет
совместимостью комбинаций стилей.

1.6.5. Связь с другими подсистемами

  • Стадия 0: безусловные рефлексы реагируют на стили и параметры.
  • Стадия 1+: контекст УР включает Level1 (базовое состояние) и Level2 (стили).
  • Стадия 2+: Δгомеостаза → AOE → `Usefulness` автоматизмов.
  • Стадия 4+: mood, Danger, VeryActualSituation питают IE и эпизодику.

1.6.6. Семантика параметров: таксономия и интерпретируемость

Числовые поля `ParameterData` задают динамику; семантика — через `Name`,
`Description` и конфигурацию эксперимента (`VitalParameters.dat`). В текущем коде
отдельного поля `ParameterCategory` нет; таксономия — соглашение исследователя,
фиксируемое в конфиге и документации прогона.

  ┌─────────────────┬────────────────────────────────────────────────────────────┐
  │ Класс           │ Смысл / роль в поведении                                   │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ Физиологические │ Поддержание «тела»: энергия, повреждения, самосохранение   │
  │ (IsVital=true)  │ Критичны для AOE, Danger, VeryActualSituation              │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ Когнитивные     │ Мотивация исследования, обучения; некритичны для выживания │
  │ (IsVital=false) │ Влияют на стили и интегральное состояние                   │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ Социальные      │ Коммуникация, поиск контакта; связаны с Operator/Niche     │
  │ (IsVital=false) │ как каналами стимуляции, так и coupling                    │
  └─────────────────┴────────────────────────────────────────────────────────────┘

  ├────┼─────────────────┼───────────┼─────────┼──────────────────────────────────┤
  │ 1  │ Голод           │ true      │ −1      │ Физиологический (дефицит)        │
  │ 2  │ Повреждения     │ true      │ +1      │ Физиологический (избыток)        │
  │ 3  │ Стресс          │ true      │ +1      │ Физиологический / когнитивный    │
  │ 4  │ Обучение        │ false     │ +1      │ Когнитивный                      │
  │ 5  │ Общение         │ false     │ +1      │ Социальный                       │
  │ 6  │ Поиск           │ false     │ +1      │ Когнитивный                      │

Дополнительная семантика агента (не параметры гомеостаза, но связана с IE):
`AgentProperties.dat` — пол, возраст, социальность (одиночка…зависимый), темперамент.
Стили (`BehaviorStyles.dat`) — мотивационные режимы, активируемые зонами параметров.

Для воспроизводимости эксперимента в `NicheInitSnapshot` (§6.11) фиксируются пути к
файлам параметров и их версия/хэш. Перенос между задачами: сохранять ID и Name;
числовые NormaWell/Weight калибруются под Niche.

1.6.7. Прото-forward-model в данных автоматизма

В `Automatizm.GomeoIdSuccesArr` хранится список ID параметров, которые действие
задумано улучшать (метаданные при создании/конверсии УР). В текущем коде поле
не участвует в runtime-выборе автоматизма — только персистентность и отладка.
Канон v3.5: это задел под forward model (§5.2.3).

2.1. Оператор: что может и чего не должен

Не является:
  • единственным источником реальности;
  • постоянным судьёй;
  • участником операционного замыкания.

Является:
  • источником формы поведения;
  • инженером эксперимента;
  • на фазе A — задатчиком начальных аттракторов.

3. АРХИТЕКТУРА КАНАЛОВ ВОЗДЕЙСТВИЯ И ОЦЕНКИ
═══════════════════════════════════════════════════════════════════════════════

3.1. Принцип (нейробиология, робототехника)

Единственный источник оценки для обучения — внутренний: динамика гомеостаза Creature.

  • В биологии обучение, управляемое наградой/ошибкой, опирается на
    интероцептивные/гомеостатические сигналы и связность «действие → изменение
    состояния» (Rovee-Collier, Gergely: обнаруженная связность; гомеостатическое
    обучение с подкреплением).

  • В робототехнике устойчивая схема: оператор воздействует на среду; агент учится
    по последствиям в среде, а не от кнопки скалярной награды (см. экологическая/
    enactive робототехника, учитель как формирователь возможностей для действия,
    не оракул).

Niche и Operator не «шлют оценку» параллельно в смысле явного педагогического ±1
(§0.4). Niche обеспечивает каузальную цепочку и материал для оценки (влияние
на гомеостаз); Operator обеспечивает педагогическую форму. Конфликт «два судьи»
возникает только при архитектурной ошибке — когда канал Operator напрямую
записывается как `UsefulnessDelta` без иерархии относительно отклика Niche.

3.1a. Влияние и оценка в коде

  • Влияние: `InfluenceActionSystem`, `HostBatchUpdateParameterValues`,
    coupling Niche→Creature — изменение `ParameterData.Value`.

  • Оценка: `ComputeOperatorAutomatizmAssessment`,
    `AutomatismResultTracker.AnalyzeResult` — извлечение знака из Δгомеостаза.

Канон: тот же механизм оценки, другой первичный триггер (окно отклика Niche, §3.4).
Смысл пользовательской формулировки сохраняется: если Niche влияет на гомеостаз
в ответ на действие, она и есть источник каузальной «оценки через отклик»;
различие — архитектурное (влияние ≠ явное сообщение о награде).

3.2. Рекомендуемая схема по фазам

  ┌───────────────┬─────────┬─────────────────────┬────────────────────────┬─────────────────────┬──────────────────────────────┐
  │ Фаза          │ Стадии  │ Прямое              │ Operator → Niche       │ Operator → Creature │ Источник полезности          │

Вывод для фазы C: Operator полностью переходит на воздействие через Niche для
рутинного обучения. Прямое влияние на Creature — аварийный режим и, опционально,
не маркированные мета-сигналы. Это упрощает архитектуру (один экологический
интерфейс) и сохраняет преимущества оператора как экспериментатора, не оракула.

3.3. Зачем сохранять прямое переопределение на фазе A

Прямое изменение параметров Creature на стадиях 0–1 не противоречит канону, если:

  • система ещё не операционно замкнута (мало связей, низкая цена интерференции);
  • переопределение трактуется как задание начальных условий, не как пошаговая
    награда;
  • явно ограничено по фазе и логируется (`AssessmentType.Bootstrap`,
    `EmergencyOverride`).

На фазах B–C рутинное прямое переопределение противоречит операционному замыканию
и создаёт выученную беспомощность / переобучение на Operator.

3.4. Переприоритизация контура ожидания оценки (текущий код → канон)

Сейчас в ISIDA: после автоматизма — `WaitingForOperatorEvaluation`; при ответе
оператора — `ComputeOperatorAutomatizmAssessment` (гомеостатические дельты от
влияния Operator).

Канон: тот же механизм извлечения Δгомеостаза, но триггер:

  1. Первичный (фаза B+): истекло окно оценки после действия и зафиксирован
     отклик Niche (изменение coupling / влияние от Niche).

  2. Вторичный: ответ Operator в контексте ритуала (зеркало, подстраивание) —
     с пониженным весом или отдельной семантикой (`AssessmentType.RitualScaffold`,
     не общий ±1).

Контур ожидания не удаляется на фазе B — переприоритизируется: сначала окно
отклика Niche, затем ритуальный канал Operator.

Реализация (§12, `TriadPhaseStagePolicy`, `CouplingBridge.SyncPhaseWithEvolutionStage`):

  • Стадия задаёт ceiling: 0–1 → max A; 2–3 → max B; 4+ → max C.
  • Стадия 4+ задаёт floor: min C (фазы A/B недопустимы).
  • При загрузке конфига, смене стадии и сохранении из UI фаза приводится к диапазону;
    при auto-clamp — запись в `triad_config.dat` и предупреждение в лог.
  • `EmergencyOverride` на InfluenceAction — вне иерархии (аварийный обход gate).

Уточнение: условные рефлексы — стадия 1, не «стадия психики». Психика включается
на стадии 2. Ошибка переноса УР на стадии психики в ранних описаниях — исправлена.

Стадии 0–5 — эвристическая схема калибровки и фазовых ограничений API, а не
онтологическая последовательность развития. В биологии рефлексы, психика и эпизодика
развиваются с перекрытием; в ISIDA стадии задают, какие подсистемы активны и какие
каналы влияния допустимы. Допустимый диапазон фазы триады привязан к стадии в коде;
эмпирическая необходимость жёсткой последовательности стадий — открытый вопрос (§10, п.10).

4.2. Фаза A (0–1)

  • Пластичность максимальна; Niche может быть почти статичной.
  • Operator: прямое переопределение и влияние допустимы.
  • Условный рефлекс: см. §5.1.

4.3. Фаза B (2–3)

  • Ритуализация: Operator демонстрирует → Creature зеркалит → Niche откликается
    → Δгомеостаз.
  • Coupling Creature→Niche обязателен.
  • Параллельный канал Operator допустим с пониженным весом.

4.4. Фаза C (4+)

  • Операционное замыкание; прямое переопределение Creature заблокировано API.
  • Рутинный Operator — только через Niche.
  • Attribution и персонификация «причины» — эпизодика, `ObjectImportanceService`,
    Understanding/IE (§5.4), не `OrientationReflexSystem`.

5.1.1. Архитектурная позиция vs биология

ISIDA реализует упрощённую модель классического обусловливания, а не полный
лабораторный CS–US протокол. Архитектурное решение: корреляция образов восприятия
в скользящем временном окне τ (`TimeWindowPulses`), CS должен предшествовать US.
Не моделируются следовые рефлексы, точная темпоральная карта CS–US интервала
и блокировка (blocking) — это осознанные упрощения MVP.

Биологическая аналогия: Rescorla–Wagner с адаптивным затуханием (см. заголовок
`ConditionedReflexesSystem.cs`).

5.1.1a. Временное окно τ (`TimeWindowPulses`)

Текущий код: фиксированное τ ∈ [1, 10] пульсов (`ConditionedReflexSettings`, default=5).
Калибруется исследователем; адаптации к контексту нет.

Канон post-MVP (рекомендация рецензии): τ_eff = τ_base · f(novelty), где
f(novelty) увеличивает окно при `AppGlobalState.IsNewConditions` (детектор
`UpdateNoveltyDetector`) — больше времени на связывание CS–US в новой ситуации.
Реализация — §10, п.11.

5.1.1b. Минимальная эвристика адаптивного τ (канон v3.6, рекомендация рецензии)

До полной адаптации по модальности — простое правило для MVP+:

  τ_eff = min(10, τ_base × (1 + 0.5 × IsNewConditions))

где `IsNewConditions` — `GomeostasSystem.UpdateNoveltyDetector`. При новизне окно
расширяется на 50%, не более 10 пульсов. Реализация в
`ConditionedReflexFormationService.CheckTemporalCorrelations` — этап 4 (§13.2).

5.1.2. Формирование (`ConditionedReflexFormationService`)

  1. `RecordStimulus(pulse, StimulusImageId, …, geneticReflexId)`:
     • geneticReflexId > 0 → безусловный стимул (US) → `_lastUnconditionedStimulus`
     • geneticReflexId == 0 → условный стимул (CS) → `_lastConditionedStimulus`
     Контекст фиксируется: BaseState (Level1), BehaviorStyleImageId (Level2), ToneId, MoodId.

  2. `CheckTemporalCorrelations(currentPulse)` (вызывается из `ReflexesActivator`
     после БР или действия/фразы оператора):
     • оба стимула в пределах τ = `TimeWindowPulses`;
     • CS.Pulse < US.Pulse (условный предшествует безусловному);
     • → `ProcessConditionedAssociation()` → создание или усиление УР.

  3. Вторичное обусловливание (`CheckSecondaryConditioning`): фраза, активирующая
     существующий УР, может породить УР 2–3-го порядка (max Order=3).

5.1.3. Математическая модель крепости (`ConditionedReflexesSystem`)

  • Образование:  C(k) = C(k−1) + α·(β − C(k−1)),  β=1, α≈0.2
  • Затухание:    C ← η^(1/C)·C,  η≈0.98 (сильные рефлексы затухают медленнее)
  • Активация:    C > γ,  γ≈0.6
  • Порядок n>1:  α' = α/K^n, начальная крепость /= K^n, K≈1.5

5.1.4. Хранение (`ConditionedReflex`)

  • Level1: интегральное базовое состояние гомеостаза
  • Level2: список ID активных стилей (контекст)
  • Level3: `StimulusImageId` — пусковой образ (`PerceptionImagesSystem`)
  • AssociationStrength, SourceGeneticReflexId, Order (1–3)
  • ToneId, MoodId — для вербальных CS

Персистентность: файлы `ConditionedReflexes`, `ConditionedReflexSettings`.

5.1.5. Активация (`ReflexesActivator`)

При наличии пускового стимула:

  1. Точное совпадение по узлу дерева рефлексов.
  2. Компаундный стимул: суммация C_combined = min(1, ΣC_i) при одном US; конкурентное
     подавление при разных US (θ_comp ≈ 0.7).
  3. Иерархическое частичное совпадение образа (подмножество Level3).
  4. Fallback на цепочку безусловных рефлексов.

`ReflexExecutionService.ExecuteConditionedReflex(id)` выполняет действия исходного БР
(`SourceGeneticReflexId`); успешное выполнение дополнительно усиливает ассоциацию.

5.1.6. Конверсия на стадии 2+

`ConditionedReflexToAutomatizmConverter` переносит устойчивые УР в автоматизмы при
переходе к психике — мост между рефлекторным и произвольным уровнем.

Attribution на стадии 1: не требуется персонификация причины («оператор vs среда»).
Достаточно фиксации нейтрального предшествующего образа, на который перецепляется
БР. Вопрос «кто вызвал» — не задача стадии 1.

5.2. Ориентировочный рефлекс (ISIDA-OR): определение и границы

5.2.1. Не смешивать с классическим ОР

Классическая ориентирующая реакция (Павлов–Соколов): реакция на новый/изменившийся
стимул; привыкание при повторении; растормаживание привыкания при изменении.

ISIDA-OR (преемник BOT, `OrientationReflexSystem`): не окно оценки после действия
и не классический ОР. Это механизм ориентации на входящий стимул после активации
дерева автоматизмов:

  • ОР1 (нет готового automatizm): обновить IE, выбрать/создать automatizm по
    genetic purpose (`OrientationReflex_1` / BOT `orientation_1`).

  • ОР2 (automatizm есть): проверить применимость в текущих условиях
    (`OrientationReflex_2` / BOT `orientation_2`).

Срабатывает на стимул (`PsychicSystem.SensorActivation`, стадии < 4), до/вместо
полного осмысления.

Отключение ISIDA-OR на стадиях ≥ 4 — архитектурный выбор ISIDA/BOT, не следствие
биологии: классическая ориентирующая реакция у взрослых не исчезает, а модулируется.

На стадиях ≥ 4 функции, связанные с ISIDA-OR, распределяются так:

  ┌─────────────────────────┬────────────────────────────────────────────────────┐
  │ Функция                 │ Механизм на 4+ (текущий код / канон)               │
  ├─────────────────────────┼────────────────────────────────────────────────────┤
  │ Детекция гомео-новизны  │ `GomeostasSystem.UpdateNoveltyDetector` →          │
  │                         │ `AppGlobalState.IsNewConditions`                   │
  ├─────────────────────────┼────────────────────────────────────────────────────┤
  │ Реакция на новизну      │ `ReflexesActivator`, прерывание automatizm chains  │
  ├─────────────────────────┼────────────────────────────────────────────────────┤
  │ Осмысление ситуации     │ УМ1/УМ2, `ThinkingCyclesSystem`, episodic rules    │
  ├─────────────────────────┼────────────────────────────────────────────────────┤
  │ Attribution             │ Episodic memory, IE, `ObjectImportanceService`     │
  └─────────────────────────┴────────────────────────────────────────────────────┘

Ограничение архитектуры: отдельного аналога ISIDA-OR1/ОР2 на стимул на 4+ нет.
Новизна детектируется через гомеостатический детектор и мышление, а не через
orientation automatizm tree path. Это зафиксированное ограничение, не неявное
допущение.

5.2.2. Оценка действия (AOE) — отдельный контур и реализация

AOE ≠ ISIDA-OR. Оценка — пост-действенный контур: после моторного автоматизма система
фиксирует снимок гомеостаза и через окно W_eval извлекает знак полезности.

5.2.2a. Конвейер оценки (текущий код, стадия ≥ 2)

```
Автоматизм выполнен
  → AutomatismResultTracker.StartTracking()
      (PreviousState, StimulusImageId, снимок параметров)
  → [окно WaitingPeriodForActionsVal тактов]
  → PsychicSystem.EvaluatePreviousAutomatizm()  [после UpdateStateOnly]
      → HomeostasisCalculator.ComputeOperatorAutomatizmAssessment()
      → AutomatismResultTracker.MarkOperatorRecognition(assessment)
          → AnalyzeResult() → UsefulnessDelta ∈ {−1, 0, +1}
          → UpdateAutomatizmUsefulness()
          → FinishTracking() → EpisodicMemoryRulesService (стадия 4+)
```

Критично: оценка выполняется после `UpdateStateOnly` на следующем пульсе, когда
гомеостаз уже отражает отклик Operator/Niche.

5.2.2b. Алгоритм `ComputeOperatorAutomatizmAssessment` → assessment ∈ {−1, 0, +1}

  1. Для каждого IsVital параметра: знаковая дельта vs снимок «до»
     (`TrySignedParameterDelta`): улучшение +1, ухудшение −1, шум 0 (порог |Speed|/100).
  2. `vitalScore` = сумма знаков по жизненным параметрам.
  3. Фокусный параметр (домinant на старте автоматизма): может определить знак,
     если vitalScore=0 и не противоречит интегральному состоянию.
  4. Fallback: `AssessmentFromOverallStates(before, after)` — сравнение Bad/Normal/Well.

5.2.2c. `AnalyzeResult` и классификация исхода

  • `RecognizedByOperator` и assessment≠0 → Success (assessment>0) / Error (assessment<0).
  • assessment=0 после истечения окна → WaitingForResponse или Skipped.
  • Без распознавания: сравнение PreviousState vs CurrentState (интегральное).

5.2.2d. Правило обучения (формализация, ответ на рецензию)

Единственный источник подкрепления — внутренний знак Δгомеостаза, не команда Operator:

  Usefulness(t+1) = clamp( Usefulness(t) + assessment, −10, +10 )

где assessment ∈ {−1, 0, +1} из AOE. Это дельта-правило с дискретным шагом ±1,
не градиентный спуск; соответствует инженерной модели накопления опыта BOT/ISIDA.

Ограничение дискретности (рецензия v3.4): три значения достаточны для MVP и
коротких цепочек; в средах с компромиссами между параметрами возможны осцилляции
выбора. Post-MVP: непрерывный assessment ∈ [−1, +1] как взвешенная сумма
`TrySignedParameterDelta` по IsVital с нормализацией по Weight (§10, п.12).

Выбор автоматизма (`GetAutomatizmFromNodeId`):
  • предпочтение штатному (`Belief=2`) при Usefulness ≥ 0;
  • иначе — максимальный Usefulness среди неотрицательных на ветке.

Пересмотр штатного (`AfterAutomatizmUsefulnessUpdated`):
  • если Belief=2 и Usefulness < 0 → переназначение штатного на лучший оставшийся
    (Usefulness ≥ 0, max Count, затем max Usefulness).

5.2.2e. Temporal credit assignment

Текущий код (MVP):

  • Один автоматизм отслеживается за такт (`WaitingForOperatorEvaluation`);
  • окно W_eval = max(WaitingPeriodForActionsVal, W_min) + LatencyPulses;
  • assessment приписывается последнему завершённому автоматизму в окне;
  • горизонт K (§5.3.1) — отделение отклика Niche от фона, не multi-step credit.

Канон v3.5 — минимальный eligibility trace (спецификация, реализация — приоритет post-MVP):

При выполнении цепочки автоматизмов (NextID, `IsAutomatizmChainActive`) ведётся
очередь последних M шагов с затухающим весом:

  e_i(t) = λ^(t − t_i)   для i-го автоматизма в активной цепочке,  λ ∈ [0.8, 0.9]

При получении assessment в окне W_eval обновление полезности:

  ΔUsefulness_k = assessment · e_k / Σ_j e_j

Параметры: M = 5…10 тактов, λ = 0.85 (стартовая калибровка). Без trace (M=1) —
текущее поведение MVP.

Ограничение: даже с trace ISIDA не претендует на полный TD(λ); достаточно для
цепочек длиной 3–7 шагов с отложенным откликом Niche. Полный RL credit assignment —
§10, п.9.

Канон v3.5: объединить извлечение Δгомеостаза с первичным триггером = отклик Niche
(§5.3), вторичным = ответ Operator (ритуал). Текущий код: триггер — ответ Operator.

5.2.3. Forward model (предиктивная оценка): текущее состояние и канон

Текущий код: оценка постфактум — AOE после отклика Niche/Operator. Внутреннего
симулятора последствий действий нет. `GomeoIdSuccesArr` — декларативные метаданные
(§1.6.7), не используется при выборе.

Канон v3.5 — упрощённый forward model (стадия 3+, post-MVP реализация):

Кэш статистики из эпизодики и AOE:

  PredictedDelta(paramId, actionImageId) = EMA( Δparam | action, context )

где EMA обновляется после каждого подтверждённого AOE на стадиях 2+; на стадии 3+
может использоваться для ранжирования кандидатов автоматизмов (не блокирует
выполнение — только bias при равной Usefulness). Инициализация: `GomeoIdSuccesArr`
как prior до первых наблюдений.

Ограничение: это не иерархическая генеративная модель (не predictive coding Фристона);
минимальный кэш «действие → ожидаемый Δгомеостаз» для снижения проб в опасных средах.

Терминология для документации:

  ┌─────────────────────────────┬────────────────────────────────────────────────┐
  │ Термин                      │ Смысл                                          │
  ├─────────────────────────────┼────────────────────────────────────────────────┤
  │ ISIDA-OR                    │ Ориентация на стимул; выбор/проверка automatizm│
  │                             │ стадии <4                                      │
  ├─────────────────────────────┼────────────────────────────────────────────────┤
  │ AOE                         │ Извлечение полезности из Δгомеостаза после     │
  │ (ActionOutcomeEvaluation)   │ действия; окно удержания; стадии ≥2            │
  ├─────────────────────────────┼────────────────────────────────────────────────┤
  │ Attribution                 │ Персонификация причины; стадии 4+; эпизодика,  │
  │ (персонификация причины)    │ значимость объектов, IE                        │
  └─────────────────────────────┴────────────────────────────────────────────────┘

Не называть AOE «ориентировочным рефлексом».

5.3. AOE и связность действия с откликом

После моторного действия Creature:

  1. Фиксируется снимок гомеостаза и состояния Niche.

  2. Открывается окно оценки длительностью `W_eval` тактов:

     `W_eval = max(WaitingPeriodForActionsVal, W_min) + LatencyPulses_contour`

     где `LatencyPulses_contour` — из активного контура (§6.8); для MVP с цифровым
     симулятором обычно 0–1.

  3. При изменении гомеостаза в окне — вычисляется знак
     (`ComputeOperatorAutomatizmAssessment` / integral state delta).

  4. Attribution образа-причины на стадиях 1–3: не обязательна; достаточно связи
     образ действия → исход.

  5. На стадиях 4+: уточнение «кто/что» через эпизодику и `ObjectImportanceService`.

Связность vs спонтанная динамика Niche: одного окна оценки недостаточно при
автономном дрейфе Niche. Это блокирующее условие реализации фазы B+, не
«отложенный» вопрос.

5.3.1. Вычитание базового фона (минимальная спецификация для MVP)

На каждый такт логирование диады фиксирует:

  • `niche_state_before`, `niche_state_after`, `creature_gomeo_before`,
    `creature_gomeo_after`;
  • `creature_action_id`, `evaluation_window_id`;
  • `niche_spontaneous_delta` — изменение Niche за окно без действия Creature
    (базовый фон);
  • `niche_response_delta` — изменение Niche, обусловленное действием
    (after − before − baseline).

Базовый фон (baseline): скользящее среднее `niche_spontaneous_delta` за последние
N тактов без моторного действия Creature.

  ┌───────────┬────────────────────────────────────────┬──────────────────┬─────────────┐
  │ Параметр  │ Назначение                             │ Стартовое (MVP)  │ Калибровка  │
  ├───────────┼────────────────────────────────────────┼──────────────────┼─────────────┤
  │ N         │ Окно baseline                          │ 10–30            │ По          │
  │           │                                        │                  │ стабильности│
  │           │                                        │                  │ фона Niche  │
  ├───────────┼────────────────────────────────────────┼──────────────────┼─────────────┤
  │ threshold │ Мин. |niche_response_delta| для        │ 0.5–2.0          │ Эксперимент │
  │           │ обусловленного отклика                 │ (ед. param)      │             │
  ├───────────┼────────────────────────────────────────┼──────────────────┼─────────────┤
  │ K         │ Горизонт корреляции action↔delta       │ 3–5              │ Эксперимент │
  │           │ (тактов)                               │                  │             │
  └───────────┴────────────────────────────────────────┴──────────────────┴─────────────┘

Альтернатива на фазе A: Niche почти статична → baseline ≈ 0, threshold минимален.

Оговорка (нестационарная Niche): скользящее среднее предполагает квазистационарный
фон. Если Niche имеет собственные рефлексы, циклы или коадаптацию, baseline может
систематически ошибаться. Для MVP статичный хост / слабо динамичная Niche (фаза A)
— достаточно. Для фазы B+ — экспериментальная верификация; при необходимости —
адаптивный baseline (EWMA с большим N) или простая модель предсказания дрейфа
Niche (после MVP).

Критерий обусловленного отклика: |niche_response_delta| > threshold и (опционально)
корреляция меток времени действий с delta на горизонте K тактов.

AOE на гомеостаз Creature: полезность считается по Δparams после вычитания
ожидаемой спонтанной составляющей (аналог `HasCriticalParameterChanges`,
игнорирующего шаг дрейфа |Speed|/100).

Без вычитания baseline AOE не включается в MVP-диаду на нетривиальной Niche
(только статичный host-Niche на фазе A).

5.3.3. Фаза B: два канала влияния (Niche + Operator)

На фазе B активны оба канала: отклик Niche (первичный) и влияние Operator
(вторичный, подстраивание). Это частный случай «множественных источников» (§6.9).

Проблема: Creature не должен приписывать Δгомеостаз от прямого влияния Operator
отклику Niche.

Решение MVP (инженерное, не эмергентное):

  1. Каждое изменение гомеостаза Creature в окне AOE помечается `StimulusOrigin`
     в логе диады / конвейере влияния: `Niche | Operator | Spontaneous`.

  2. Первичный AOE считается только по дельтам с `StimulusOrigin=Niche` (после
     coupling), внутри `[action_pulse .. action_pulse + W_eval]`.

  3. Влияние Operator с `AssessmentType.RitualScaffold` не участвует в первичном
     AOE; учитывается отдельно как вторичный канал (зеркало, ритуал), с
     пониженным весом или без обновления полезности automatizm.

  4. На фазе C рутинный Operator идёт только через Niche → проблема двухканальности
     снимается.

Ограничение MVP: Creature не выучивает отображение nicheParam↔creatureParam;
различение каналов — на стороне движка по `StimulusOrigin`, не в конвейере
восприятия.

5.4. Attribution и «различение агентов» (стадии 4+)

Не утверждается: полное эмергентное различение operator/environment с стадии 0
без структуры; строгое предиктивное кодирование (Friston) — в ISIDA нет явной
иерархической генериативной модели.

Фактически на 4+: attribution через эпизодическую память, правила
(`EpisodicMemoryRulesService`), деревья понимания, IE, значимость объектов —
символические/эпизодические механизмы, не движок ошибки предсказания.

Механизм (упрощённо): при AOE на 4+ `EpisodicMemoryRulesService` записывает правило
«образ действия + контекст → Effect=UsefulnessDelta»; `ObjectImportanceService`
накопляет значимость объектов из повторяющихся исходов; Understanding/IE связывает
образы с темами. Эмергентное различение operator/environment без врождённых priors
или иерархической генеративной модели не гарантируется — это архитектурное
ограничение, зафиксированное честно (рецензия §5.4).

Инженерная разметка происхождения стимула (`StimulusOrigin`):

  • Не передаётся в конвейер восприятия/обучения Creature (симбионт не «видит»
    метку).

  • Обязательна для исследователя: логи, API, `ResearchLogger`, фазовое ограничение,
    `AssessmentType`.

  • Используется для воспроизводимости экспериментов и A/B-тестов эмергентной
    attribution.

Врожденные смещения (связность, значимость новизны) допустимы как genetic/
parameter priors без нарушения канона.

5.5. Коадаптивная стабилизация сенсомоторных контуров («ритуализация»)

Формирование устойчивого блока из цепочки automatisms через подстраивание,
зеркалирование (стадия 3), AOE после отклика Niche. Термин «ритуал» сохранён
для совместимости с педагогической терминологией ISIDA; формально — коадаптивная
стабилизация повторяющихся сенсомоторных контуров. Условные рефлексы и automatisms —
субстрат, не синоним процесса.

Схема:

  1. Operator демонстрирует последовательность (или провоцирует через Niche).
  2. Creature отзеркаливает (стадия 3) или выполняет под подстраиванием.
  3. Niche реагирует; Creature фиксирует AOE.
  4. Повторение → automatizm chain → интериоризация.
  5. Стадии 4+: контур — объект рефлексии и эпизодические правила.

5.5.1. Зеркалирование (`MirrorAutomatizmService`, стадия 3)

Решение проблемы correspondence (рецензия): не эмергентное, а структурное
сопоставление через общий репертуар `ActionsImagesSystem`.

  1. Operator предъявляет стимул (фраза / команда / в ObservationMode — флажок
     воздействия) → распознаётся узел дерева автоматизмов (`detectedNodeId`).
  2. `TryCreateInitialParrotAutomatizm`: создаётся «попугайский» автоматизм
     «стимул оператора → ответ оператора» с `Belief=1` (чужие сведения).
     `InfluenceActionId` связывает образ действия с действием пульта для копирования.
  3. После AOE положительной оценки: `TryCreateMirrorFromPendingOperatorResponse`
     формирует пару сдвиг + эхо на разных BranchID (инвариант: один Belief=2
     на ветку).
  4. `Belief`: 0=предположение, 1=чужие сведения, 2=проверенное собственное знание.
     Переход 1→2 — через накопление положительных AOE.

Ограничение: зеркалирование работает для вербальных/командных стимулов; невербальные —
только в `ObservationMode`. Полное motor correspondence для произвольных тел —
post-MVP.

5.6. Подстраивание и угасание

Ослабление поддержки Operator архитектурно принудительно задано (API блокирует
прямое переопределение на 4+). Причина: автономия и прямой контроль — структурные
антагонисты (операционное замыкание).

6.3. Разметка происхождения (для исследователя)

`StimulusOrigin: Operator | Niche | CreatureSelf | Unknown` — в логах и API;
не в конвейере восприятия Creature.

6.4. Прямое вмешательство Operator

  • Creature: A — да; B — ограниченно; C — заблокировано (кроме Emergency).
  • Niche: только тривиальное равновесие, экологический коллапс, калибровка;
    всё логируется.

6.5. Тактовая архитектура диады

`Niche.Update → Coupling → Creature.Update` на такт. Требует контекста уровня
экземпляра (`IsidaContext` на движок), не глобальные `GlobalTimer` /
`AppGlobalState` для мультиагентного режима.

6.6. MVP и тест переноса

  • Creature (полный стек) + Niche (профиль роли §1.4) + Operator (с фазовым
    ограничением).
  • Логирование диады каждый такт (§5.3.1).
  • Тест переноса: обучение на Niche₁ → перенос на Niche₂ (та же структура
    coupling, другие параметры) без переобучения Operator.

6.7. Протокол coupling (Niche ↔ Creature): минимальный контракт данных

Направление Creature → Niche:

  1. `AdaptiveActionsSystem.ApplyAction(actionId)` → CouplingBridge.
  2. CouplingBridge читает `CouplingTarget` из конфига действия (см. ниже) и
     применяет `Δparameter` к `GomeostasSystem` Niche.
  3. Niche может породить reflex / реактивный automatism → вторичные изменения
     состояния Niche.

CouplingTarget vs `TargetGomeoParamIdArr` (важно):

  ┌─────────────────────────┬──────────────────────────────┬─────────────────────────────┐
  │ Поле                    │ Семантика в текущем коде     │ Семантика для MVP-диады     │
  ├─────────────────────────┼──────────────────────────────┼─────────────────────────────┤
  │ TargetGomeoParamIdArr   │ ID параметров гомеостаза     │ Унаследованное; для         │
  │                         │ Creature, «на кого           │ coupling не использовать    │
  │                         │ направлено»                  │ напрямую                    │
  ├─────────────────────────┼──────────────────────────────┼─────────────────────────────┤
  │ CouplingTarget (новое,  │ —                            │ nicheParamId, delta, scale —│
  │ конфиг CouplingBridge)  │                              │ параметры Niche, изменяемые │
  │                         │                              │ действием Creature          │
  └─────────────────────────┴──────────────────────────────┴─────────────────────────────┘

MVP: отображение `actionId → CouplingTarget[]` в конфиге эксперимента; опционально
дублировать `TargetGomeoParamIdArr` для UI/унаследованного без coupling.

Направление Niche → Creature:

  1. Статическая таблица отображения: `nicheParamId → creatureParamId, scale,
     lag_pulses` (конфиг эксперимента).
  2. Применение через `HostBatchUpdateParameterValues` (Creature) с
     `StimulusOrigin=Niche`.
  3. Частота: 1 раз за такт после `Niche.Update`, до `Creature.Update` (§6.5).

Ограничение MVP (явное): отображение задаётся исследователем, Creature не
обнаруживает связь параметров самостоятельно.

Канон выученного coupling (§10, п.6 — минимальный механизм post-MVP):

  1. Лог диады фиксирует тройки (actionId, ΔnicheParam[], ΔcreatureParam[]) за W_eval.
  2. При повторении ≥ N раз (N≈5) с корреляцией |ρ| > ρ_min (≈0.6) — гипотеза связи
     nicheParam_j → creatureParam_k записывается в эпизодические правила (стадия 4+).
  3. Подтверждение через AOE (положительный исход при предсказанном направлении Δ)
     → правило повышает confidence; иначе — decay.

До реализации — статическая таблица §6.7 обязательна для MVP.

6.8. Контракт контура: минимальный интерфейс

Contour — адаптер между внешним миром и Niche.

  ┌─────────────────┬────────────────────────────────────────────────────────────┐
  │ Поле            │ Смысл                                                      │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ ContourId       │ Идентификатор источника (office_api, sim_physics,          │
  │                 │ ros_sensors)                                               │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ TickHz /        │ 1 замер на такт `GlobalTimer` (или буфер с меткой pulse)   │
  │ PulseSync       │                                                            │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ InputSnapshot   │ См. формат ниже                                            │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ OutputHooks     │ Действия Creature → API / исполнительные механизмы         │
  │                 │ (через CouplingBridge)                                     │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ LatencyPulses   │ Задержка отклика контура в тактах; увеличивает `W_eval`    │

Формат `InputSnapshot` (MVP):

```text
InputSnapshot {
  pulse: int
  values: float[Dim]   // Dim фиксирован для ContourId
  range: [0.0 .. 100.0] per channel (нормализация до параметров Niche)
}
```

Отображение `InputSnapshot.values[i] → nicheParamId` — в конфиге контура. Dim
и диапазоны фиксируются для каждого ContourId для воспроизводимости переноса.

Задержка и AOE: если `LatencyPulses > 0`, окно оценки должно включать задержку
(`W_eval` см. §5.3), иначе обусловленный отклик даёт ложный `NoResponse`.
MVP-диада: контуры с `LatencyPulses ≤ 1` (цифровой симулятор, статичный хост).
Перенос sim→real с большей задержкой — после MVP или расширенный `W_eval` +
верифицированный baseline.

Contour питает Niche, не Creature.

9. ФОРМАЛЬНАЯ ФОРМУЛА
═══════════════════════════════════════════════════════════════════════════════

> Creature адаптируется в Niche. Niche влияет на гомеостаз Creature через
> coupling — это каузальная обратная связь; знак «оценки» извлекает Creature
> (AOE), Niche не шлёт явный ±1. Operator на стадии 0 задаёт первичные
> настройки; до стадии 4 ослабляет прямое воздействие на гомеостаз; с 4+
> рутинное вмешательство — только через Niche, финализируя переход к
> выживанию в среде, а не у оператора. Обучение начинается в педагогической
> песочнице (§0.7); перенос — в эксплуатационные контуры. ISIDA-OR (<4),
> attribution (4+), разметка происхождения — для исследователя. Триада —
> минимальная единица автономного развития.

12.3. Тактовый цикл (`GlobalTimer.ProcessAgentPulse`)

Пульс ≈1 с (настраивается). `GlobalTimer.Start()` запрещён при стадии 0.

```
[≥4] ThinkingThemePulseResolver.ResolveAtPulseStart(pulse)
→ OnPulseBeforeGomeostasis(pulse)          // хост / зачаток Niche
→ GomeostasSystem.UpdateStateOnly()
→ if IsDead → stop
→ OnPulseAfterGomeostasisBeforePsychic     // сценарии Operator: стимул пульта
→ PsychicSystem.ProcessPsychicPulse(...)
→ ConditionedReflexesSystem.UpdateAgentLifetime()  [≥1]
→ if !IsSleeping → ReflexesActivator.ProcessReflexPulse(...)
→ ResearchLogger.FlushBufferedAgentRowToMemoryNow()
→ AdaptiveActionsSystem.CleanupExpiredReflexActions()
→ [≥4] ThinkingThemePulseResolver.RecordEndOfPulseAgentEvents()
→ OnPulseCompleted(pulse)
→ finally: IsNewConditions=false; ReflexesActivator.ResetStates
```

Критично для AOE: стимул Operator вставляется после `UpdateStateOnly`, до
`ProcessPsychicPulse`; оценка автоматизма — в начале следующего `ProcessPsychicPulse`
(после следующего `UpdateStateOnly`), не в `SensorActivation`.
