# Анализ определения тем мышления: ISIDA vs BOT и план доработки

## 1. Текущее состояние в ISIDA

### 1.1 Где задаётся тема

- **Единственное место активации темы:** `UnderstandingTreeSystem.ActivateSituation()` → `RunNewThemeSimplified(situationImageId, hasStimulusFromPult)`.
- **Вызовы ActivateSituation:** только из `PsychicSystem` (пробуждение и после активации дерева автоматизмов), т.е. тема меняется только при активации дерева понимания.

### 1.2 Логика RunNewThemeSimplified (фактически 2 ветки)

В `UnderstandingTreeSystem.cs` (строки 179–199):

```csharp
private int RunNewThemeSimplified(int situationImageId, bool hasStimulusFromPult = false)
{
  // ...
  int typeId = 0;
  if (hasStimulusFromPult && _situationTypeSystem != null)
  {
    typeId = _situationTypeSystem.GetThemeTypeIdBySituationTypeId(6);  // только тип 6
    if (typeId <= 0) typeId = _themeImageSystem.DefaultThemeTypeId;
  }
  var (id, _) = _themeImageSystem.CreateThemeImageOrGet(2, typeId, pulsCount);
  return id;
}
```

Итог:

- **Ветка 1:** есть стимул с пульта → тема берётся **только** из типа ситуации с ID = 6 (жёстко зашит), иначе `DefaultThemeTypeId`.
- **Ветка 2:** нет стимула с пульта → `typeId = 0` → в `CreateThemeImageOrGet` подставляется `DefaultThemeTypeId`.

То есть реально используются только **два варианта** определения типа темы: «тема по типу ситуации 6» и «тема по умолчанию». Тип текущей ситуации (`situationImageId` → `SituationTypeId`) в выборе темы не участвует.

### 1.3 Инфраструктура, которая уже есть

- `ThemeImageSystem` — 17 дефолтных типов тем (1–17), справочник типов, вес, PulsCount.
- `SituationTypeSystem.GetThemeTypeIdBySituationTypeId(situationTypeId)` — привязка типа ситуации (1–10, 41–60) к типу темы.
- У образа ситуации есть `SituationTypeId`: его можно получить как `_situationImageSystem.GetById(situationImageId)?.SituationTypeId`.
- В `ActivateSituation` уже есть `situationImageId`, `_situationImageSystem`, `_situationTypeSystem`, `_themeImageSystem`.

То есть механизм «тип ситуации → тип темы» и доступ к типу текущей ситуации уже есть, но в `RunNewThemeSimplified` не используются.

## 2. Текущее состояние в BOT

### 2.1 Количество и разнообразие определений темы

Тема задаётся через `runNewTheme(kind, weight)` во многих местах и по разным событиям.

**По месту вызова (файл → тип темы, вес):**

| Файл | Тип темы (ThemeTypeStr) | Условие/событие |
|------|-------------------------|-----------------|
| `understanding_tree.go` | needRunNewTheme (2 или 11) | После активации дерева ситуации (needRunNewTheme задаётся в automatism_tree) |
| `automatism_tree.go` | 11 (Действие оператора) | При любом действии оператора (ActivationTypeSensor > 1) |
| `automatism_tree.go` | 2 (Негативный эффект ментального автоматизма) | Негативный эффект после ожидания ответа оператора (effect < 0) |
| `understanding_process.go` | 2 | Негативный эффект ментального автоматизма |
| `understanding.go` | 12 (Сомнение в штатном автоматизме) | Очень актуальная/опасная ситуация, нужно подумать об автоматизме |
| `understanding_functions.go` | 10 (Непонимание) | Состояние непонимания (isConfusion) |
| `mental_automatizm_INFO_functions.go` | 16 (Есть объект высокой значимости) | Два сценария с высокой значимостью |
| `importance.go` | 16 | Объект высокой значимости |
| `automatizm_result.go` | 7 (Игнорирование оператором) | Истекло ожидание ответа оператора |
| `understanding_theme_image.go` (someThemeDetection) | 10, 5, 8, 8, 13, 14, 15, 9 | По настроению, опасности, базовым контекстам (поиск, игра, защита, страх, агрессия, неудовлетворённость) |

**Итого в BOT:** порядка 10+ точек вызова и 17 типов тем; тема зависит от:

- типа ситуации / активации дерева (needRunNewTheme);
- наличия и характера стимула оператора (11, 2, 7);
- результата оценки автоматизма (2, 12);
- состояния понимания (10);
- значимости объектов (16);
- контекста «настроение + окружение» в `someThemeDetection` (5, 8, 9, 13, 14, 15).

### 2.2 someThemeDetection в BOT

Вызывается перед концом объективного вызова `consciousnessElementary()`. По сути — отдельный слой детекции темы по текущему состоянию:

- Плохо и опасно: тема 10 (Непонимание), вес 3.
- Хорошее настроение, нет опасности: поиск (5), игра (8), обучение (8) по базовым контекстам.
- Базовые контексты: защита (13), страх (14), агрессия (15), неудовлетворённость (9).

Тема и вес задаются явно в коде под каждое условие.

## 3. Сравнение

| Аспект | ISIDA | BOT |
|--------|--------|-----|
| Число мест, где задаётся тема | 1 (только при активации дерева понимания) | 10+ (дерево, оператор, результат автоматизма, важность, непонимание, контекст) |
| Учёт типа ситуации для темы | Нет (используется только тип 6 при стимуле с пульта) | Да (needRunNewTheme из контекста активации + тип ситуации) |
| Учёт результата действий оператора | Нет | Да (негативный эффект → тема 2, игнор → 7) |
| Учёт сомнения в автоматизме | Нет | Да (тема 12) |
| Учёт непонимания | Нет | Да (тема 10) |
| Учёт высокой значимости | Нет | Да (тема 16) |
| Отдельный «детектор темы» по состоянию | Нет | Да (someThemeDetection по настроению и контексту) |
| Вариативность веса темы | Фиксирован 2 | Разные веса (1–5) в зависимости от важности |

Итог: в ISIDA тема определяется по сути двумя событиями (стимул с пульта → тип 6, иначе — тема по умолчанию), в BOT — по многим событиям и с разными весами.

## 4. План реализации более вариативного определения тем в ISIDA

### 4.1 Принципы (по аналогии с BOT)

1. Использовать **текущий тип ситуации** для выбора типа темы (через уже существующую привязку в `SituationTypeSystem`).
2. Добавить **дополнительные точки** вызова создания/обновления темы (не только при активации дерева понимания).
3. По возможности ввести **отдельный слой** определения темы по состоянию (аналог `someThemeDetection`), с приоритетом по весу/важности.
4. Разрешить **разные веса** темы в зависимости от контекста (как в BOT).

### 4.2 Этап 1: Тема от типа текущей ситуации (минимальное изменение)

**Цель:** уйти от «только тип 6 или default» и использовать тип реально активной ситуации.

**Что сделать:**

1. В `RunNewThemeSimplified` получать тип ситуации по текущему образу:
   - из `_situationImageSystem.GetById(situationImageId)?.SituationTypeId` (если в дереве понимания хранится именно ID образа ситуации);
   - либо передавать в `ActivateSituation`/`RunNewThemeSimplified` не только `situationImageId`, но и `situationTypeId` (если он уже есть в месте вызова), чтобы не дублировать обращение к SituationImageSystem.
2. Вызывать `_situationTypeSystem.GetThemeTypeIdBySituationTypeId(situationTypeId)` для **любого** полученного `situationTypeId` (1–10, 41–60), а не только для 6.
3. Если для данного типа ситуации тема не задана (0), тогда:
   - при наличии стимула с пульта можно по-прежнему подставлять тему типа 6 или запасной вариант;
   - иначе — `DefaultThemeTypeId`.
4. Настроить в конфигурации/справочнике привязки типов ситуаций (1–5, 6–10, 41–60) к типам тем по смыслу (аналогично BOT: ответное действие, запуск автоматизма, нужное осмысление, эксперимент, игнор оператора и т.д.), чтобы один раз задать соответствие, а не хардкодить только тип 6.

**Результат:** при одной точке вызова тема будет различаться по типам ситуаций (1–5 и при необходимости 6–10, 41–60), а не по двум веткам «стимул с пульта / не стимул».

### 4.3 Этап 2: Дополнительные события, задающие тему

**Цель:** приблизить поведение к BOT: тема меняется не только при активации дерева понимания, но и при других значимых событиях.

Предлагаемые точки (по аналогии с BOT) и что передавать в `CreateThemeImageOrGet` (или в обёртку типа RunNewTheme):

| Событие | Тип темы (примерный ID по справочнику ISIDA) | Вес | Где в ISIDA вызывать |
|---------|----------------------------------------------|-----|----------------------|
| Действие оператора (стимул с пульта) | 11 «Действие оператора» | 1–2 | При формировании контекста активации с пульта (уже частично есть; можно явно выставить тип 11 и вес) |
| Негативный эффект ментального автоматизма | 2 | 2 | После оценки результата действия оператора (аналог understanding_process / automatism_tree в BOT): при отрицательной оценке — вызвать создание темы 2 |
| Игнорирование оператора (истекло ожидание) | 7 | 2 | При срабатывании «ожидание ответа истекло» (аналог automatizm_result) |
| Сомнение в штатном автоматизме | 12 | 5 | В блоке принятия решения о запуске автоматизма: когда решено «нужно подумать об автоматизме» (аналог understanding.go) |
| Непонимание | 10 | 1–3 | При фиксации состояния непонимания/новизны (если такое состояние в ISIDA выделено) |
| Объект высокой значимости | 16 | 2 | При обновлении значимости объекта (модуль важности/значимости), если такой есть |

Для каждого из этих мест нужно:

- определить точку в коде (сервис/обработчик), где событие уже обрабатывается;
- вызвать там `ThemeImageSystem.CreateThemeImageOrGet(weight, themeTypeId, pulsCount)` и передать выбранную тему в контур мышления/дерева проблем (как сейчас передаётся themeId из `ActivateSituation`).

Важно: в BOT при смене темы также перезапускается цикл размышления и учитывается конкуренция по весу. В ISIDA нужно решить, достаточно ли только обновить themeId в ProblemTreeInfo и связанных структурах или нужен явный «перезапуск цикла» и сравнение веса с текущей темой (аналог `runNewTheme` с проверкой веса).

### 4.4 Этап 3: Детектор темы по состоянию (аналог someThemeDetection)

**Цель:** один централизованный вызов перед завершением «объективного» цикла мышления, который по текущему состоянию (настроение, опасность, контекст) выставляет тему, если она ещё не задана или новая важнее.

**Что сделать:**

1. Выделить метод типа `ThemeDetectionByState()` (или встроить в существующий «конец объективного цикла» в PsychicSystem/Understanding), вызываемый в том же месте, где завершается обработка одной «объективной» активации (аналог конца `consciousnessElementary` в BOT).
2. Внутри метода описать правила по аналогии с BOT:
   - плохо + опасно + очень актуально → тема 10 (Непонимание), вес 3;
   - хорошее настроение, нет опасности: по контексту (поиск, игра, обучение) → темы 5, 8 с подходящими весами;
   - контексты защита/страх/агрессия/неудовлетворённость → темы 13, 14, 15, 9 с весами.
3. Для каждого правила вызывать `CreateThemeImageOrGet` с нужным весом и при необходимости сравнивать с текущей темой по весу (если в ISIDA введётся хранение текущей темы и её веса).
4. Контексты и «базовые состояния» брать из уже существующих в ISIDA (настроение, флаги опасности, типа ситуации и т.д.); при отсутствии — ввести минимальный набор полей/флагов.

Это даёт вариативность «по состоянию», не привязанную только к одному месту активации дерева.

### 4.5 Этап 4: Вес темы и конкуренция тем

**Цель:** как в BOT — более важные темы (выше вес) могут перекрывать текущую.

**Что сделать:**

1. Хранить в состоянии психики/движка не только текущий themeId, но и вес текущей темы (или получать его из ThemeImageSystem по themeId).
2. При любом вызове «установить тему» (из этапов 1–3) сравнивать вес новой темы с текущей; менять тему только если новая имеет больший вес (или при равенстве — по дополнительному правилу, например «более свежая»).
3. В точках из этапа 2 задавать веса осознанно (например, сомнение в автоматизме — 5, игнор оператора — 2), как в BOT.

Так определение темы станет не только более вариативным, но и устойчивым к «перескокам» на менее важные темы.

### 4.6 Порядок внедрения (рекомендуемый)

1. **Этап 1** — тема от типа текущей ситуации в `RunNewThemeSimplified`: быстро даёт разнообразие по типам ситуаций без новых точек вызова.
2. **Этап 4 (базово)** — ввести хранение текущей темы и веса и проверку при установке темы в `ActivateSituation`, чтобы следующими шагами не сломать приоритеты.
3. **Этап 2** — по одному событию (например, сначала «негативный эффект», потом «игнор оператора», потом «действие оператора» и т.д.), с вызовом создания темы и обновлением текущей темы с учётом веса.
4. **Этап 3** — детектор по состоянию, вызываемый в конце объективного цикла, с учётом веса и текущей темы.
5. При необходимости — донастройка привязок типов ситуаций к темам в справочнике и весов в коде.

### 4.7 Риски и ограничения

- **Обратная совместиость:** если в конфигурации или данных уже завязано «тема только от типа 6», после этапа 1 поведение изменится; нужна проверка сценариев и при необходимости флаг «старое поведение» на переходный период.
- **Производительность:** дополнительные вызовы `CreateThemeImageOrGet` и обращение к `GetById`/`GetThemeTypeIdBySituationTypeId` — минимальны; критично только не вызывать детектор по состоянию слишком часто.
- **Тестирование:** после каждого этапа проверять сценарии: только дерево понимания, стимул с пульта, истекшее ожидание, негативный эффект, высокая значимость (если реализовано).

## 5. Краткое резюме

- В ISIDA тема сейчас определяется по **двум** по сути событиям (стимул с пульта → тип ситуации 6, иначе default), в **одной** точке кода.
- В BOT тема задаётся в **многих** местах по разным событиям (тип ситуации, оператор, результат автоматизма, непонимание, значимость, контекст) и в отдельной функции `someThemeDetection` по состоянию, с разными весами.
- Чтобы сделать в ISIDA более вариативное определение тем по аналогии с BOT: (1) использовать тип текущей ситуации для выбора темы в `RunNewThemeSimplified`; (2) добавить вызовы установки темы при других событиях (негативный эффект, игнор, сомнение в автоматизме, непонимание, высокая значимость); (3) ввести детектор темы по состоянию; (4) ввести вес темы и конкуренцию по весу при смене темы.

Код в этом документе не изменяется; план рассчитан на последующую реализацию в коде по этапам выше.
