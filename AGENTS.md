# AGENTS.md — Правила проекта ISIDA (движок)

Движок симбионта (`isida.dll`). UI-хост и адаптеры (AIStudio, Velum) — отдельные репозитории; здесь только ядро: гомеостаз, рефлексы, психика, деревья, сценарии.

## Общие принципы

- **Простота прежде всего.** Делай задачу максимально просто. Не усложняй там, где не нужно.
- **Факты важнее предположений.** Не галлюцинируй. Проверяй факты (код, логи, сборку), прежде чем предлагать изменения.
- **Действуй, а не только описывай.** При создании или изменении кода всегда используй инструменты для реальных правок в файлах.
- **Не предполагай доступность библиотек/синтаксиса.** Убеждайся, что конструкция допустима в C# 7.3 и что сборка реально есть в зависимостях.

## Протокол отладки — `DEBUG_CASEBOOK_1.md`,  `DEBUG_CASEBOOK_2.md` и т.д.

Рядом с этим файлом лежит **протокол разобранных ошибок** проекта: симптом → гипотезы (включая тупиковые) → корень → исправление → эвристики.

- **Перед тем как искать причину бага — прочитай разделы «Эвристики» и «Указатель случаев» в `DEBUG_CASEBOOK_1.md`.** Если симптом похож на описанный, начинай с уже известного корня, а не с обхода кодовой базы. Заведомо тупиковые ветки из протокола **не повторять**.
- **После каждого успешно исправленного бага — добавь случай** в `DEBUG_CASEBOOK_1.md` по шаблону из этого же файла (включая опровергнутые гипотезы), и, если правка обобщается, новую эвристику. Это обязательная часть работы.
- **После исправления бага — по возможности добавь регрессионный тест** в `tests\Isida.Tests` (xUnit), чтобы баг не «реанимировался». Тест должен воспроизводить именно ошибочный сценарий (граничные случаи, «до/после»). См. раздел «Тесты».
- Если файл стал слишком большим — заведи следующий (`DEBUG_CASEBOOK_2.md` и т.д.) и обнови ссылки.

## Компиляция

Корень проекта — рабочая директория (`D:\Программы\ISIDA\Programms\isida`), файл проекта — **`isida.csproj`** (не SDK-style, .NET Framework 4.8).

**Сборка из корня (предпочтительно):**

```powershell
dotnet build "isida.csproj" -c Debug --no-restore
```

**Если `dotnet build` недоступен — MSBuild:**

```powershell
& "${env:ProgramFiles}\Microsoft Visual Studio\2022\Community\MSBuild\Current\Bin\MSBuild.exe" `
  "isida.csproj" /t:Build /p:Configuration=Debug /v:minimal
```

- **Считай задачу по коду выполненной только если сборка Debug прошла без ошибок.** Предупреждения не игнорировать без причины (в этом проекте CS1591/CS1573 — ошибки, см. ниже).
- После правок, затрагивающих компиляцию (`*.cs`, `isida.csproj`, новые/удалённые `Compile`), **обязательно пересобирай** и исправляй все ошибки, не оставляя по одной в IDE.
- Если менял публичные API, используемые в AIStudio/Velum, — после пересборки isida пересобери хост.
- Конфигурации: только `Debug|AnyCPU` и `Release|AnyCPU`.

## Тесты

Регрессионные тесты (xUnit) — в отдельном проекте **`tests\Isida.Tests\Isida.Tests.csproj`** (`net48`, SDK-style, `LangVersion 7.3`). Ссылка на движок — `HintPath` на `..\..\bin\Debug\isida.dll`.

**Перед тестами обязательно собрать `isida.dll`** (сам `isida.csproj` в тестовый solution не входит).

```bash
dotnet restore tests\Isida.Tests\Isida.Tests.csproj
dotnet test tests\Isida.Tests\Isida.Tests.csproj --no-restore
# один класс/метод:
dotnet test tests\Isida.Tests\Isida.Tests.csproj --no-restore --filter "FullyQualifiedName~GlobalTimerPulseRaceTests"
```

- `InternalsVisibleTo("Isida.Tests")` объявлен в `Properties\AssemblyInfo.cs` — тестам доступен `internal`.
- Инфраструктура живого движка: `EngineFixture` + `EngineIntegrationTestBase`, коллекция `[Collection("EngineIntegration")]` с `DisableParallelization = true`. Фикстура поднимает цепочку гомеостаз→рефлексы и **не** инициализирует `GlobalTimer`/`PsychicSystem`/`ReflexesActivator` — для тестов пульсации/выгрузки поднимай нужные части явно (см. `GlobalTimerPulseRaceTests`) и используй отдельную коллекцию без параллелизма.
- Тесты двигают время движка **детерминированным счётчиком пульсов** (`EngineFixture.AdvancePulses`), без `DateTime.Now`/`Thread.Sleep` (кроме явных тестов синхронизации).
- Новый тестовый `.cs` в SDK-style-проекте подхватывается автоматически (в отличие от `isida.csproj`).

## Регистрация файлов в проекте (`isida.csproj`)

Проект **не SDK-style**: MSBuild **не** подхватывает `*.cs` автоматически. Любой новый исходник нужно **вручную прописать** в `isida.csproj`, иначе он не войдёт в сборку (CS0246 «тип не найден», «типы не видны» в IDE).

- **Новый класс:** `<Compile Include="Common\MyClass.cs" />` в соответствующем `<ItemGroup>` (группировать по папкам: `Common\`, `Gomeostas\`, `Psychic\`, `Reflexes\`, `Actions\`, `Sensors\`, `Scenarios\` и т.д.).
- Переименование/удаление файла — **синхронно** править `isida.csproj`.

**Чек-лист перед концом задачи:** (1) каждый новый/переименованный файл указан в `isida.csproj`; (2) сборка проходит, нет CS0246 из-за забытых `Include`; (3) удалённые с диска файлы убраны из `isida.csproj`.

## Язык C#

- Проект зафиксирован на **C# 7.3** (`<LangVersion>7.3</LangVersion>` в `isida.csproj`). **Не использовать** синтаксис C# 8+/9+ (`is not`, `record`, `init`, switch-выражения, `with`, nullable-аннотации и т.п.) без явного повышения версии языка в проекте.

## XML-комментарии (обязательно, без исключений)

`DocumentationFile` включён; **CS1591 и CS1573 трактуются как ошибки сборки.**

- **Каждый** публично видимый тип, класс, интерфейс, перечисление — `<summary>`.
- **Каждое** публичное/защищённое свойство, поле, константа — `<summary>`.
- **Каждый** публичный/защищённый метод — `<summary>`; **для каждого параметра — свой `<param name="...">`** (если описан хотя бы один `<param>`, описать нужно все, иначе CS1573 = ошибка); для возвращаемого значения — `<returns>`; при выбросе исключений — `<exception cref="...">`.
- **Каждый** публичный/защищённый конструктор — `<summary>`, `<param>`, при необходимости `<exception>`.
- Пиши XML-документацию **сразу** при написании/изменении кода, не откладывай. Перед концом правок проверь отсутствие CS1591/CS1573.
- `<see cref="..."/>` — только на реально разрешимые из метаданных типы/члены, иначе CS1574/CS0419; при неоднозначности — полная ECMA-ссылка (`M:Namespace.Type.Method(...)`).

## Архитектура движка

- **Единая точка сборки систем — `Common\IsidaEngine.cs`** (`IsidaContext`). Контекст владеет системами, сохраняет ссылки как явные свойства (`context.SomeSystem`) и передаёт их «вниз» через конструкторы / методы вторичной инициализации (`SetDependencies`, `SetPsychicSystemDop` и т.п.).
- **Порядок инициализации односторонний и зависимостно-безопасный:** не использовать систему до её инициализации; при циклических зависимостях — явные методы вторичной инициализации. Шаги инициализации нумерованы и строго упорядочены — сохранять нумерацию и комментарии-якоря.
- **Выгрузка — в `IsidaContext.Dispose()` через `SafeDispose(...)`** в зависимостно-безопасном порядке (сверху вниз по зависимостям; double-dispose безопасен). Держать `IsFullyInitialized` в синхроне с новыми обязательными системами.
- **Не глотать критические сбои инициализации молча:** сохранять цепочку `IsidaInitializationException` с корректным шагом.
- Сохранять обратную совместимость `Create()` / `CreateWithDefaults()`.
- Пульсация — только через `ISIDA.Common.GlobalTimer` после `IsidaEngine.Create`; стадии эволюции для запуска пульса ≥ 1.

## Без `*.Instance` и перекрёстных ссылок

- **Запрещено** обращаться к другим классам через глобальный синглтон (`SomeSystem.Instance.Method()` / `.Property`) внутри класса, которому нужна эта система. Использовать **только ссылку (поле), переданную в конструктор / `SetDependencies` / иной метод вторичной инициализации**.
- **Не создавать перекрёстных зависимостей через `IsidaEngine`/контекст:** контекст — единственное место, где собираются ссылки сразу после инициализации системы; системы не обращаются к контексту или друг к другу через общий «хаб». Если A нужна B — в `IsidaEngine` после инициализации B вызывают `context.A.SetB(context.B)`, а не наоборот.
- **Плохо:** внутри сервиса вызвать `UnderstandingTreeSystem.Instance.UpdateThemeByTrigger(8)`.
  **Хорошо:** параметр `UnderstandingTreeSystem understandingTreeSystem` в методе, поле `_understandingTreeSystem`, установка через `SetUnderstandingTreeSystem(...)` из `IsidaEngine`.
- Явный поток изменений для разделяемого мутабельного состояния (`ReaderWriterLockSlim` или эквивалент).

## Нулевые коды параметров в деревьях

При логике **построения и обхода деревьев** (эпизодическая память, дерево автоматизмов, дерево проблем) считать **0 рабочим значением**, а не «параметр не задан», для:

- **Состояние (BaseID)** — 0 = «Норма» (−1 Плохо, 1 Хорошо);
- **Тон (Tone)** — 0 может быть валидным идентификатором тона;
- **Настроение (Mood)** / в эпизодической памяти **EmotionID** — 0 может быть валидным.

**Не** определять «глубину заданных условий» по правилу «первый встреченный 0 = параметр отсутствует» — иначе ветки с состоянием/эмоцией 0 обрабатываются неверно (неправильное ветвление, «матрёшка»). Узел считать совпавшим только при полном совпадении по всем уровням (BaseID, EmotionID, NodePID, …); иначе создавать ребёнка у текущего родителя. В комментариях к `GetTrueLevel`, `CheckBranchFromCondition`, `AddBranch`, обходу дерева — явно указывать, что для Состояние/Тон/Настроение 0 является рабочим значением.

## Создание нового класса — стандарты

- Реализовать `IDisposable` с безопасной одноразовой очисткой (`_disposed` guard).
- Если класс владеет персистентными данными — по умолчанию вызывать сохранение из `Dispose()` (с учётом стадии/валидации).
- Зарегистрировать сервис в `Common\IsidaEngine.cs`: свойство в `IsidaContext`, шаг инициализации в правильном порядке, звено в цепочке выгрузки.
- Код организовывать в осмысленные `#region` (инициализация, состояние, основная логика, файловый ввод-вывод, выгрузка и т.п.).
- Предпочитать ссылки через конструктор/инициализатор вместо прямого `*.Instance` внутри логики.
- Новая логика не должна ломать существующую: сохранять обратно-совместимые дефолты, не трогать несвязанные пути выполнения.
- После правок: собрать `isida.csproj`, исправить внесённые предупреждения/ошибки, убедиться, что порядок init/dispose корректен.

## Работа с файлами: доступные инструменты

Не вызывать несуществующие инструменты (`grep`, `rg`, `find` из shell и т.п.) — использовать инструменты из таблицы.

| Задача | Инструмент | Параметры |
|--------|------------|-----------|
| Список файлов/папок в каталоге | `list_directory` | `path` (абсолютный), опц. `ignore` |
| Чтение одного файла (текст, изображение, PDF) | `read_file` | `absolute_path`, опц. `offset`+`limit` |
| Чтение нескольких файлов / по glob-маскам | `read_many_files` | `paths` (массив), `include`, `exclude` |
| Поиск по **содержимому** (regex) | `search_file_content` | `pattern`, опц. `path`, `include` |
| Поиск файлов по имени/маске | `glob` | `pattern`, опц. `path` |
| Запись/создание файла целиком | `write_file` | `file_path`, `content` |
| Точечная замена фрагмента в файле | `replace` | `file_path`, `old_string`, `new_string`, опц. `expected_replacements` |
| Выполнение shell-команды | `run_shell_command` | `command`, опц. `directory`, `timeout` |
| Web-поиск / документация | `google_web_search`, `docs_search`, `web_fetch` | — |

**Правила, чтобы не зацикливаться:**

1. Перед правкой — сначала `read_file` целевого участка (минимум 3 строки контекста) и/или `search_file_content`, чтобы найти все места. Не строить догадок о содержимом файлов.
2. Для точной правки — `replace` с точным `old_string` (включая отступы и переносы). Для нового файла / полной перезаписи — `write_file`.
3. Пути к инструментам — абсолютные (корень проекта + относительный путь).
4. `search_file_content`/`glob` с `path` указывай на **директорию**, а не на файл.
5. Параллельные независимые вызовы (несколько поисков/чтений) запускай одним сообщением.
6. После изменения кода — проверить **сборку** (`dotnet build isida.csproj -c Debug --no-restore`) и **тесты** (см. «Тесты»).
