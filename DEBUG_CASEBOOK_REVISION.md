# DEBUG_CASEBOOK_REVISION.md — Регламент ревизии базы случаев ISIDA

Назначение: **база случаев (`DEBUG_CASEBOOK_1.md`, далее CB1) полагается истинной на 100%** — агент начинает разбор бага с неё и берёт известный корень как факт. Если в базе есть внутреннее противоречие (случай A говорит «X истинно», случай B — «X ложен»), агент зацикливается: он не может одновременно верить обоим. Поэтому базу надо **регулярно перетряхивать**: искать противоречия, снимать их правкой описаний (когда вся база + код указывают на одну ошибку описания) либо выносить в список на доп. проверку (когда уверенности нет).

Этот файл — **реестр ревизий**: что уже снято, что спорно, как проверять. Он не заменяет случаи, а ссылается на них. Методология идентична `VELUM/DEBUG_CASEBOOK_REVISION.md`.

## 2. Категории находок

| Категория | Что это | Что делать |
|---|---|---|
| **Ложная пара (A ⟺ ¬A)** | Ранний случай утверждает X, поздний — ¬X; оба помечены «Исправлен» | Снять правкой описания, если код/тест/поздний случай с доказательством однозначно на одной стороне: в раннем — пометка `⚠ УТОЧНЕНО случаем N (E…)`; в позднем — ссылка. Эталон: 46 ⟺ 48 |
| **Контур удалён рефакторингом** | Случай корректен на дату написания, но описывает код/тесты, позже **удалённые** целиком (`git log --diff-filter=D`) | Случай НЕ «врал» — он устарел. Обязательна пометка `⚠ КОНТУР УДАЛЁН (<хэш> <дата>)`; вопрос «архивировать/удалить случай» — в спорные (раздел 4), решение за оператором |
| **Устаревшее утверждение** | Более поздний случай/код опроверг раннюю формулировку, текст остался | Пометка `⚠ УТОЧНЕНО случаем N (E…)`; правка допустима, т.к. вся база указывает на одну ошибку описания |
| **Описка статуса/числа** | Указатель/статус/счётчик тестов противоречит фактическому исходу | Исправить описательно (без изменения корня/даты). Эталон: случай 11 «554/552» |
| **Сомнительный случай** | Противоречие НЕ снимается текстом — нужна эмпирика (ручная проверка или доп. тест) | Внести в раздел 4 «Спорные случаи», не править утверждения |

**Правило безопасности:** править текст описания можно **только** когда противоречие снимается всей базой и/или живым кодом (есть более поздний случай с доказательством по коду/логам/тесту, либо явная опечатка, либо факт из `git`). Если для снятия нужен эксперимент на живой машине — это **не** правка описания, а запись в спорные.

### 2.1. Уровни доверия [A]–[D]

Каждому случаю/эвристике присваивается **дискретный** уровень доверия — не числовой вес. Числа плавают при каждой ревизии и требуют пересчёта всей базы; дискретный ранг стабилен, дёшев и читается без калибровки.

| Уровень | Что значит | Как брать в работу |
|---|---|---|
| **[A] Живой регресс / код HEAD** | Подтверждено зелёным регресс-тестом, реально существующим в HEAD, или прямым чтением текущего кода | Факт без перепроверки |
| **[B] Лог / ручной прогон** | Корень найден эмпирически (лог, ручной сценарий), но автотеста нет | Факт; при сомнениях — быстрый ручной повтор |
| **[C] Текст базы / git-факт** | Снято более поздним случаем, опечаткой или фактом из `git` (напр. `8aaf9dd`) | Верно логически; при первом обращении сверить якорь с кодом |
| **[D] Спорное / не снято** | Из раздела 4; противоречие текстом не снимается | НЕ брать на веру; работает **стоп-гейт** (см. 4.0) |

**Присвоение.** Новый случай по умолчанию: **[B]**, если есть лог/ручной прогон; **[C]**, если снято текстом/git. **[A]** — только когда назван конкретный зелёный тест из HEAD. **[D]** — всё, что попало в раздел 4. Уровень пишется коротким тегом в шапку/заголовок случая. Эмпирика (A/B) всегда бьёт текст (C): при конфликте текст не удаляется, а помечается `⚠ УТОЧНЁН` и понижается до уровня живого свидетельства.

**Эталон присвоения (CB1):** путь A строго 2-я стадия (случай 48) — **[A]** (`GetAutomatizmByGeneticPurpose_Stage3_PathAClosed_DoesNotCreateClone` в HEAD); удалённый контур мотор→стимул (4.1) — **[C]** (git-факт `8aaf9dd`, закрыт архивированием 2026-11-23); мёртвая ветвь `EvolutionStage == 3` в ОР1 (4.2) — **[A]** после удаления ветви из `OrientationReflexSystem.cs` (была **[D]** на первичной ревизии).

## 3. Чек-лист ревизии (проход по новому случаю)

1. **Новый номер не занят?** Поискать `## Случай N` и `E{номер}` по всем `DEBUG_CASEBOOK_*.md`. Занят → пометка о коллизии. *(В CB1 на ревизии 2026-11-23 коллизий нет: случаи 1–49, эвристики E1–E53 — все уникальны.)*
2. **Новая эвристика не противоречит ли старой?** Если новая обобщает/сужает/отменяет старую — в старой пометка `⚠ УТОЧНЕНО/ОТМЕНЕНО случаем N`. Эталон: E50←48, E52←48.
3. **Тот же симптом уже разобран?** Если да — это должно быть **дополнением** к существующему случаю, а не новым. Если заведён новым — проверить, не создаёт ли он ложную пару «A ⟺ ¬A» (см. раздел 4.1).
4. **Ссылки на код живы?** Якоря `Файл.cs:строка`, имена методов/классов сверить с текущим кодом (`search_file_content`). Расхождение → либо правка якоря (не меняя корня), либо пометка `⚠ КОНТУР УДАЛЁН`. **Обязательно после любого рефакторинга:** `git log --diff-filter=D --name-only` и `git log -S "<имя удалённого метода>"`.
5. **Статус в указателе = фактический исход?** Удалённый/отменённый механизм не может значиться «Исправлен» без пометки (эталон: случай 12).
6. **Счётчики тестов непротиворечивы?** Формат `X/Y` требует `X ≤ Y`; «X>Y» — описка (эталон: случай 11 «554/552»).
7. **Нет ли «трёх заплаток на одну дыру»?** Если один симптом закрыт несколькими случаями с **разными** механизмами — записать в спорные.

## 4. Спорные случаи (нужна доп. проверка, текстом НЕ снимаются)

Формат: что оспаривается → как проверить → вариант закрытия (новый/исправленный регресс-тест или ручная проверка).

### 4.0. Стоп-гейт (правило входа)

Если в реестре есть спорный случай уровня **[D]**, **релевантный текущей задаче** (совпадает симптом/подсистема/эвристика), то **сначала закрывается противоречие, и только потом заводится новый случай**. Иначе новый случай наслаивается на непроверенное основание и сам становится **[D]** — база разрастается петлями.

Порядок при срабатывании гейта:
1. Найти в разделе 4 запись, покрывающую спор (`4.1`…`4.N`).
2. Прогнать её «Как проверить» (регресс / ручной сценарий / `git`).
3. Закрыть: повысить доверие до [A]/[B]/[C] либо зафиксировать решение оператора.
4. И только затем — новый случай по исходной задаче.

Исключение: если закрыть спор прямо сейчас невозможно (нужна живая машина/SolidWorks, которой нет), новый случай заводится, но **обязательно** с явной ссылкой на `4.N` и уровнем **[D]**, чтобы не притворяться достоверным.
