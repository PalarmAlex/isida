# DEBUG_CASEBOOK_ARCHIVE.md — Архив удалённого контура ISIDA

Назначение: сюда **перенесены** случаи активной базы `DEBUG_CASEBOOK_1.md` (CB1), которые описывают **удалённый** оперантный контур мотор→стимул и транзитивных цепей условных рефлексов. Контур удалён коммитом `8aaf9dd` («refactor(Reflexes): remove operant (motor->stimulus) learning layer», 2026-10-30, 3129 строк, 14 файлов). Проверено в HEAD: `MotorStimulusAssociationSystem`, `BuildTransitiveChain`, `IsTransitive`, `TransitiveReflexIds`, `GetActivatableStimuli`, `TryGetNextChainStimulus`, `SetLastMotorAction`, `_heldMotorActionId`, `_motorStimulusLinkConsumed` — **ноль вхождений** в `*.cs`.

Регресс-тесты этих случаев (`MotorStimulusAssociationTests`, `MotorStimulusChainReplayTests`, `TransitiveChainLoggingTests`, `TransitiveReplayIntegrationTests`) удалены вместе с кодом — утверждение «регресс зелёный» для них **невыполнимо**.

**Как читать этот архив.** Случаи корректны на дату написания, но описывают уже несуществующий код. Это методологический архив: разборы и эвристики полезны при проектировании будущих конвейеров, синхронизированных с внешним контуром (шаги, подтверждение завершения, контекст звена, дельта-логи). В живой движок ISIDA на HEAD их переносить нельзя — ищите актуальный контур в `CB1`, а не здесь.

Правила ведения — те же, что в CB1 (`DEBUG_CASEBOOK_REVISION.md`): случаи не перенумеровывать, не удалять; кодировка файла — **UTF-8 с BOM**; править только файловыми инструментами.

## Случай 13. Цепочки у-рефлексов (реплей виртуальных стимулов): бесконечный цикл при повторном реплее одного стимула

- **Дата / сборка:** 2026-10-17, движок ISIDA (Debug, `dotnet build isida.csproj -c Debug` → 0 warning / 0 error, `dotnet test tests\Isida.Tests` → 581/581).
- **Симптом:** при обучении цепочки у-рефлексов через мотор→стимул ассоциации (`MotorStimulusAssociationSystem`) и последующем реплее виртуальных стимулов реплей зацикливался: если мотор М2 ассоциирован со стимулом С6, то при попытке реплея С6 `TryGetNextChainStimulus` возвращал тот же С6 снова и снова — цепочка не завершалась. Пользователь наблюдал «бесконечный повтор одного стимула» вместо последовательного прогона цепочки С4→С5→С6.
- **Область:** `Reflexes\ConditionedReflexFormationService.cs` — `TryGetNextChainStimulus`, `MotorStimulusAssociationSystem.GetActivatableStimuli`.
- **Гипотезы и проверки:**
  1. *`GetActivatableStimuli` возвращает неправильный список* — **опровергнуто кодом**: метод корректно возвращает все стимулы с C ≥ γ для данного мотора (проверено тестами `MotorStimulusAssociationTests`).
  2. *Цепочка должна проверять уникальность стимула* — **подтверждено**: `TryGetNextChainStimulus` выбирал первый `activatable[0]`, но не проверял, не был ли этот стимул уже отреплейнут в текущей цепочке. Если мотор М2 ассоциирован только со С6, то при шаге 3 цепочки `GetActivatableStimuli(М2)` → [С6] → С6 возвращался снова и снова.
  3. *Достаточно добавить флаг «стимул отреплейнут»* — **подтверждено**: решение — `HashSet<int> _chainReplayedStimuli`, который пополняется при каждом реплее и фильтрует выбор.
- **Корень:**
  - `TryGetNextChainStimulus` не помнил, какие стимулы уже были отреплейнуты в текущей цепочке;
  - `GetActivatableStimuli` возвращал те же стимулы при каждом вызове (нет внутренней мутации);
  - при отсутствии защиты от цикла реплей «застревал» на одном стимуле, если мотор→стимул ассоциация давала только один стимул.
- **Доказательство:** `ConditionedReflexFormationService.cs` (до правки): `TryGetNextChainStimulus` → `activatable[0]` без проверки уникальности; тест `FullCycle_TrainThenReplay_WorksTwoSteps` падал на шаге 3 (`step3` возвращал true вместо false).
- **Исправление:** `Reflexes\ConditionedReflexFormationService.cs`:
  - добавлено поле `HashSet<int> _chainReplayedStimuli` — память об отреплейнутых стимулах текущей цепочки;
  - `RecordConditionedReflexActivation`: при step==0 очищает HashSet и добавляет триггер (защита от повтора первого стимула);
  - `TryGetNextChainStimulus`: ищет первый `activatable` стимул, НЕ в HashSet; добавляет выбранный в HashSet; если все стимулы в HashSet → завершение цепочки (`step = 0`);
  - `ResetChainState`: очищает HashSet;
  - тест `FullCycle_TrainThenReplay_WorksTwoSteps` обновлён: шаг 3 ожидает false (завершение).
- **Проверка:** `dotnet build isida.csproj -c Debug` → 0 warning / 0 error; `dotnet test tests\Isida.Tests` → 581/581 (включая `MotorStimulusChainReplayTests.FullCycle_TrainThenReplay_WorksTwoSteps`).
- **Эвристики:** → E14.

## Случай 21. Транзитивная цепь: звено запускалось «как мотор», без сверки с контекстом гомеостаза, в котором выучено

- **Симптом:** в прогоне `Scenario_8.dat` после экспорта (метрика отпустила → состояние «Плохо» сменилось на «Хорошо») в статусной строке панели задач показывалось действие «Сохранить» при состоянии «Хорошо», хотя мотор этого у-рефлекса выучен и запускался в контексте «Плохо» (другая база, другой стиль). Мотор берётся через `ExecuteConditionedReflex` → `GetActionsForGeneticReflex` → `ExecuteAdaptiveActions` → `ApplyAction(actionId)` — это просто добавление в `_activeActions` без проверки контекста. ## Случай 23. Обучение цепочки не идёт поверх прокачанных у-рефлексов: цепь рвётся ровно на «известном» стимуле

- **Дата / сборка:** 2026-10-27, движок ISIDA (Debug, `dotnet build isida.csproj -c Debug` → 0 warning / 0 error).
- **Симптом:** в симуляторе сценарий оперантного обучения формирует цепочку, если в начале стоит сброс всех у-рефлексов («чистый лист»). Формулировка пользователя: «обучать можно только действиям на новые стимулы; если хоть один попадается уже известный — цепочка в этом месте разорвётся».
- **Область:** `Reflexes\ConditionedReflexFormationService.cs` (`SetLastMotorAction`, `TryStrengthenMotorStimulusLink`, поля `_lastMotorActionId`/`_lastMotorPulse`/`_motorStimulusLinkConsumed`); порядок вызовов в `Reflexes\ReflexesActivator.cs` (`ActiveFromPhrase` → `ExecuteReflexes` → `RecordStimulus`).
- **Гипотезы и проверки:**
  1. *«Застрявший» `_lastUnconditionedStimulus` блокирует `TryStrengthenNeutralSequentialLink` (гипотеза внешней нейросети: US, висящий на CS₂, навсегда отрезает сенсорные связи дальше)* — **опровергнуто кодом и тестом**: проверка уже интервальная (`_lastUnconditionedStimulus.Pulse > prevPulse && .Pulse < currentPulse`) — US «после» CS₂ не попадает в интервал следующей пары; поведение закреплено `TransitiveLearningIntegrationTests.RecordStimulus_UsBetweenCs_BreaksChain`. План «заменить single-US на список US» лечил несуществующую причину и **откачен**.
  2. *Kamin blocking (`ComputeCompetitionSuppression`) обнуляет подкрепление нового CS* — **опровергнуто**: он подавляет создание/усиление **УР**, а не мотор→стимул связь; в симптоме связь не растёт именно в мотор→стимул контуре.
  3. *«Подкрепление размазывается между УР и мотор→стимул»* — **опровергнуто**: `MotorStimulusAssociationSystem.StrengthenLink` — независимое RW (свои α/β), никакого общего пула с УР нет.
  4. *`TryStrengthenMotorStimulusLink` не усиливает связь, когда на CS уже есть УР* — **подтверждено кодом (корень)**: связь не усиливается не из-за наличия УР как факта, а из-за **мотора-реакции**, который этот УР выполнил в том же пульсе.
- **Корень:**
